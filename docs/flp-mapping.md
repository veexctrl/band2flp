# FL Studio mapping and exporter research

## Boundary

GarageBand parsing populates the neutral `Project`, `Track`, and `Region` model. The FLP writer consumes that model and must report fields that are missing or uncertain. It must not fill unknown region lengths or MIDI values with guesses.

## Current conversion coverage

| GarageBand information | Current neutral representation | Export status |
| --- | --- | --- |
| Summary tempo | `Project.tempo_bpm` | Exported when present; saved FLP is reparsed and the value is checked |
| Summary time signature | `Project.time_signature` | Exported when present; saved FLP is reparsed and numerator/denominator are checked |
| Audio placement start | `Region.start_beats` | Exported as playlist position in template PPQ ticks |
| Audio track number | `Track.index` plus raw candidate in `Region.unknown` | High confidence for audio preview fixture; cross-fixture mapping needs validation |
| Audio source | `Region.source` and `MediaReference` | Extracted into a user-selected media directory and referenced by a sampler channel |
| Audio duration/source offset/trim/loop | Duration unknown; nonzero offset unsupported | Default export rejects unknown duration; explicit `source-full` uses complete source length as a placeholder. Trims, loops, and stretching are not reconstructed. Nonzero offsets are rejected. |
| MIDI placement to `MSeq` | Candidate records in `Project.project_data` | Not transferred to neutral tracks yet; track and timing semantics remain unconfirmed |
| MIDI note to placed `MSeq` | Candidate event indices in `Project.project_data` | Fixture-specific shared-chunk relation; note fields remain hypotheses |
| Automation, sections, track mixer state | Unknown or unparsed | Not exported |

## PyFLP capability probe

A local PyFLP 2.2.1 copy was tested without adding it to project dependencies. Under Python 3.10 it parsed the installed FL Studio 2025 blank project template and saved a byte-identical round trip. The parsed project reports one arrangement, 96 PPQ, and an empty playlist. Its arrangement model exposes 500 virtual rows. Appending one candidate playlist record through PyFLP's `PlaylistEvent` and saving/reparsing preserved the fields, but this did not verify a playable audio clip or an FL Studio GUI load.

The same PyFLP copy fails to parse that template under Python 3.14 with `TypeError: <enum 'EventEnum'> has no members`. The same error is reported against PyFLP 2.2.1 on Python 3.12 in upstream [issue #183](https://github.com/demberto/PyFLP/issues/183); a proposed fix remains an [open pull request #196](https://github.com/demberto/PyFLP/pull/196) as of this research. The repository currently requires Python 3.11 or newer, so compatibility with its supported runtimes is not established. PyFLP 2.2.1 declares GPL-3.0; keep it optional until runtime compatibility is established.

For a local-only compatibility probe, adding a sentinel member to PyFLP's base `EventEnum` internal maps allowed the installed copy to parse, save, and reparse the blank template under Python 3.14. This relies on unsupported enum internals and is not used by project code.

### FL Studio 25 template check

The installed FL Studio executable reports version 25.1.5.4976. The three available empty templates under that installation all report FLP project version 24.2.99.4720 when read through PyFLP. FL Studio 9 is also present on the machine but is not used for exporter research. The FL Studio 25 executable is the target runtime. Its older-version empty project is a reasonable seed because newer FL Studio releases can open older projects; actual load/save validation in the FL Studio 25 application is still required before claiming it.

The template and generated probes remain local and ignored. No FL Studio template, demo project, proprietary plugin state, GarageBand media, or private song content is committed.

## Experimental audio export

The CLI now offers `band2flp export-flp PROJECT OUTPUT --template EMPTY.flp --media-dir NEW_MEDIA_DIR`. It uses a user-supplied empty FL Studio template, extracts uniquely embedded audio, creates audio clip channels and playlist clips, and writes a `.band2flp.json` report beside the FLP. Exact fractional beat strings are converted to PPQ ticks with rational arithmetic. PyFLP 2.2.1 is loaded optionally and is not declared as a project dependency because its GPL-3.0 licensing and runtime support remain unresolved.

The default `--length-policy reject-unknown` refuses to export if any audio region duration is unknown. `--length-policy source-full` opts into using each complete source file's frame count to estimate the clip duration at project tempo. The resulting clip length is only a placeholder: GarageBand trim, loop, and playback-stretch behavior is not recovered. The command refuses nonzero source offsets and requires each source to resolve to uniquely embedded audio. The Python 3.12+ workaround modifies PyFLP 2.2.1 enum internals; it is isolated to the exporter and must be replaced if upstream fixes the issue.

Parser tests cover WAVE and CAF timing metadata and rejection of unknown lengths. A private local integration probe produced an FLP with six audio channels and ten playlist items from one user-supplied project; PyFLP reparsing preserved positions and lengths. FLP-018 adds an exact source-path check to that round-trip. The user reports that candidates v4 through v8 trigger FL Studio's invalid-playlist warning. FLP-009 through FLP-011 document isolated probes for playlist offsets, the audio channel's resample flag, and polyphony slide; none resolved the warning. FLP-012 and FLP-013 document the sample-path event-order observation. A further inspection found that generated playlist clips decode onto rows one position below the corresponding names; FLP-014 records this likely row-mapping defect and the exporter now aligns names and clips. Project names, paths, and media remain local. FL Studio GUI acceptance and playback are not verified, so the exporter remains experimental.

## Remaining exporter work

1. Establish a supported PyFLP/runtime combination, including the project's Python 3.11+ range, or choose a different maintained writer.
2. Validate that the latest candidate opens without invalid-playlist warnings and that clip rows align with their names; confirm audio paths and playback.
3. Recover region duration, trimming, looping, stretching, and source offsets before claiming arrangement-faithful audio export.
4. Reject or clearly diagnose regions with unresolved timing or missing media. Never silently invent their values.
5. Add MIDI patterns and notes only after GarageBand note and placement semantics are validated.
6. Reopen generated output with PyFLP and FL Studio, then compare exported track and clip positions with the neutral project.

## Experiments

- **FLP-001:** Blank-template parse/save/reparse. The template round-tripped byte-for-byte through PyFLP 2.2.1 under Python 3.10. Python 3.14 parsing failed as described above.
- **FLP-002:** Playlist-event serialization probe. One synthetic playlist event survived PyFLP save/reparse. It was not linked to a resolved audio sampler and was not loaded in the FL Studio GUI; this confirms serializer mechanics only.
- **FLP-003:** FL Studio 25 installation/template check. The installed executable reports 25.1.5.4976, while all three bundled empty templates tested report project version 24.2.99.4720. The older FL Studio 9 installation was excluded. No claim of FL Studio 25 GUI load/save validation is made from this check.
- **FLP-004:** Python 3.14 compatibility shim probe. A local sentinel member in PyFLP's `EventEnum` internals enabled blank-template parse/save/reparse. This is experimental only; upstream's same error report is tracked in #183, and the proposed fix in #196 remains open.
- **FLP-005:** Local arrangement/audio serialization probe. Starting from the installed empty template, PyFLP created six sampler channels, five named playlist tracks, and ten audio playlist items from the private fixture's recovered starts. All six local media paths and the playlist position/length fields survived PyFLP save/reparse. Clip lengths deliberately use each complete source duration as a placeholder because GarageBand region trims and loops remain unknown. The `.flp`, sidecar, and extracted media are ignored local files; FL Studio 25 GUI loading and media playback have not yet been checked.
- **FLP-006:** Implemented the experimental `export-flp` command with an optional PyFLP backend, duration-policy guard, WAVE/CAF frame probing, FLP save/reparse verification, and a JSON report. The private local integration emitted six audio channels and ten clips, with all playlist positions and lengths preserved through PyFLP round-trip. This is a serializer check only; FL Studio 25 GUI load and playback remain unverified. Automated suite: 27 tests passed.
- **FLP-007:** Added explicit post-save/reparse assertions for recovered tempo and meter. A local integration using the installed FL Studio 25 blank template, optional PyFLP 2.2.1 compatibility shim, and private extracted media preserved both project clock settings along with all playlist records. The assertion paths also have unit tests for matching values and changed/lost settings. This validates PyFLP serialization and parsing only; loading or playback in the FL Studio GUI remains unverified. No template, FLP, media, or song-specific clock values are committed.
- **FLP-008:** The user reported that FL Studio 25 warns that playlist clips in the previous local export are invalid and will be deleted. Comparison with installed FL Studio demo projects identified two structural differences: the exporter emitted type-0 Sampler channels instead of type-4 audio clip channels, and it filled the undocumented 28-byte extended clip tail with zeros. Inspected valid audio clips use type 4 with an empty internal plugin name; valid extended records observed so far have nonzero tails, while valid base-size 32-byte records also exist. The exporter now creates and round-trip-checks type-4 sample channels and selects the base-size playlist layout so it does not fabricate the unknown tail. A new local candidate passed PyFLP save/reparse, with every playlist item resolving to an audio channel. It still needs an FL Studio 25 GUI load test. The invalid prior FLP remains local and should not be treated as a successful export.
- **FLP-009:** The user confirmed that `clock-roundtrip-check-v4.flp` still raises FL Studio's invalid-playlist-clips warning. A read-only scan considered 60 installed FL Studio 25 demonstration projects; 41 parsed successfully. Among 7,602 playlist entries resolving to a type-4 channel with an empty plugin name and a sample path, 1,498 used 32-byte base records with `start_offset=-1.0` and `end_offset=-1.0`; none used `0.0/0.0`. A local copy of v4 was changed only in these two fields and saved/reparsed as `clock-roundtrip-check-v5-offset-probe.flp`; PyFLP preserved all 10 items' positions, lengths, channel indices, row indices, and 32-byte record size. The user then reported the same warning on the next GUI check. The `-1/-1` pair is a repeated serialization pattern, but its semantics are unconfirmed and that change alone did not fix loading.
- **FLP-010:** Compared audio channel event values from v5 with sample-backed type-4 channels in 30 FL Studio 25 demonstration projects. All 46 sampled reference channels had `ChannelID.SamplerFlags` value 2 (40 cases) or 258 (6 cases); v5's cloned blank-sampler channels had value 3. In PyFLP's field map, bit 0 is `Resample`; both observed reference values leave it clear, while value 3 sets it. A local v6 probe clears only this bit on the six channels; PyFLP reparsing confirms six values of 2 and byte-equivalent playlist fields for all ten clips compared with v5. This makes the resample bit a HIGH-CONFIDENCE structural discrepancy and a HYPOTHESIS for the warning's cause; the GUI result is still required.
- **FLP-011:** The user reports that v6 and v7 still trigger the invalid-playlist warning in FL Studio 25. v7 changed only `Polyphony.slide` to 500 relative to v6, matching the value found on all 46 sampled audio-channel references; its playlist records remained unchanged on PyFLP reparse. Together, the GUI checks reject the offset, resample-bit, and slide-value changes as sufficient fixes. Those channel values remain common reference patterns, but are not evidence for the warning's cause. Next isolate the playlist/channel serialization against a minimal audio clip saved by FL Studio 25 itself; do not ask for another candidate check until a specific structural difference has been identified.
- **FLP-012:** With the user's authorization, inspected 12 local FLP references read-only; no project names, paths, or audio were retained in the repository. PyFLP parsed all 12. Fourteen sample-backed type-4 channels with empty internal plugin names were found, linked to 12 playlist rows. In each matching channel, `SamplePath` followed `PingPongLoop`; the generated v7 channel instead placed `SamplePath` immediately before `PingPongLoop` on all six channels. This is a concrete serialization difference and a HYPOTHESIS for the warning's cause. The exporter now places `SamplePath` after `PingPongLoop`. A local v8 candidate still needs FL Studio 25 GUI validation. The reference projects parse as FL Studio versions 21 through 24.
- **FLP-013:** Compared against the user's local FL Studio Projects folder read-only. The first 60 FLPs all parsed as FL Studio 25.1.5.4976 and contained 209 sample-backed type-4 channels with empty internal plugin names. In all 209 channels, `SamplePath` follows `PingPongLoop`; all six generated v7 channels had the reverse event order. PyFLP could decode playlist data for 36 of the 60 projects, yielding 131 rows that resolve to those channels (92 32-byte records and 39 60-byte records). It could not decode playlist events in 24 projects because their event sizes did not match its supported record layouts. The 32-byte `-1/-1` offsets appeared in 75 of the 131 decodable rows, so that pair alone is not the observed v7 discrepancy. The v8 probe changes only sample-path ordering from v7. This substantially strengthens the ordering hypothesis, but FL Studio GUI validation is still needed to confirm it fixes the warning.
- **FLP-014:** The user reports that v8 still raises the invalid-playlist-clips warning, and clips are not visible in the arrangement while track names are. PyFLP inspection of the local v8 candidate showed playlist clips on rows that did not carry the corresponding names. A first adjustment to the recovered-track-to-row mapping did not solve the mismatch: a synthetic one-clip export still reparsed with its name on row 0 and its playlist item on row 1. This shows the earlier fix was insufficient; FL Studio warning behavior is still unexplained. No private audio was inspected or copied.
- **FLP-015:** Built synthetic exports from a blank FL Studio template with one generated WAV and audio clips on recovered track indices 0 and 5. After separating the playlist row from PyFLP's track-event storage index, save/reparse placed `GarageBand Track 01` with its clip on row 1 (`track_rvidx=498`) and `GarageBand Track 06` with its clip on row 6 (`track_rvidx=493`). This confirms row/name alignment through PyFLP serialization for these two indices and template only. It does not validate FL Studio GUI acceptance, explain the invalid-playlist warning, or test the private song's media paths. No GarageBand project or audio was used.
- **FLP-016:** Added `research/scripts/flp_channel_inventory.py` to compare generated sample-backed type-4 channel event layouts with FLP references while reporting aggregate counts only. On a path-sorted scan of 100 local FL Studio 25.1.5.4976 projects, 326 type-4 sample-backed channels were found. All six generated v8 channels shared one event-ID sequence; it occurred exactly in 285 reference channels, and every generated event ID appeared in the references. For those 285 channels with the same event order, 16 of 18 comparable scalar fields matched every reference, one matched 282, and one matched 9. The latter is `PluginID.Icon` (155): its generated value is uncommon, but also occurs in valid reference channels. `PluginID.Data` was absent in 299 of 326 references and present in the rest; the generated channels omit it. Neither observed difference is a universal explanation for the invalid-playlist warning. Other nonscalar channel values, playlist serialization, and GUI acceptance remain open. The probe emitted no project names, paths, media paths, or field values.
- **FLP-017:** Added `research/scripts/flp_playlist_inventory.py` to compare static playlist record fields for generated audio rows against local FLP references. On the same path-sorted scan of 100 local FL Studio 25.1.5.4976 projects, 174 sample-backed audio rows were decoded (110 32-byte records and 64 60-byte records), with no project parse failures. The v8 candidate had ten 32-byte audio rows. Each of its seven compared static fields (`pattern_base`, `group`, `u1`, `flags`, `u2`, `start_offset`, `end_offset`) matched at least one 32-byte reference row, every complete candidate profile occurred in references (56 occurrences each), and all five distinct candidate track-row values occurred in references. This weakens the simple hypothesis that those individual static fields or row values are absent from valid projects; it does not identify why FL Studio warns or validate GUI acceptance. Output is aggregate-only and includes no project names, paths, clip timing, media paths, or field values.
- **FLP-018:** The exporter previously verified only that each saved audio channel retained a non-null sample path; it did not verify that the path still named the source selected for that channel. The round-trip now checks exact path-string equality and fails with a diagnostic if PyFLP changes it. A synthetic export using one generated WAV and a local blank FL Studio template passed save/reparse with one channel and one playlist item. This verifies the serializer path for a synthetic file only; private-media accessibility, the reported missing-file problem, FL Studio GUI loading, and playback remain unverified.
- **FLP-019:** A read-only scan of 30 local FL Studio 25 projects found playlist payloads consistent with an 80-byte record layout: at that stride, 372 candidate rows were identified and 369 item indices linked to audio-clip channels under the observed index bound. Competing 60-byte and 32-byte interpretations produced fewer channel links (43 and 71). Byte inspection through IDA MCP matched a selected 80-byte record against the ordinary Python read exactly. The 80-byte interpretation is supported by this aggregate evidence, but record framing remains a HIGH-CONFIDENCE interpretation rather than a confirmed format rule: divisibility is ambiguous, and the current inventory script only decodes 32- and 60-byte rows. A local v9 probe was built with ten 80-byte rows, retaining each prior 32-byte base and using opaque tail patterns observed in local references. PyFLP's current inventory therefore does not correctly classify this probe. No tail-field semantics are claimed. FL Studio GUI acceptance, arrangement visibility, and media playback remain unverified; the candidate and all references stay local.
